# KFR 6.3.1：大点数 DFT 的内存占用分析

问题：200M 点的 DFT 占用约 10 GB 内存。

## 内存都用在哪里

`dft_plan<T>(N)` 除了用户自己的输入、输出缓冲区以外，还需要两块大小约为 N 个复数的内存：

| 内存块 | 大小 | 来源 |
|---|---|---|
| `plan.data`（旋转因子表） | ≈ N × sizeof(complex&lt;T&gt;) | 每个 stage 存 `repeats × (radix−1)` 个旋转因子，各 stage 加起来正好约等于 N−1 |
| `plan.temp_size`（scratch） | ≈ N × sizeof(complex&lt;T&gt;) | 各 stage 都是 out-of-place 计算，最后还有一个 reorder stage，所以中间结果需要一块乒乓缓冲区 |

以 200,000,000 = 2⁹·5⁸ 为例，KFR 把它分解为 1 个 radix-2 stage 和 8 个 radix-10 stage，再加 1 个 reorder stage。其中第一个 stage 的旋转因子表就有 N/2 个复数（f32 下 800 MB），第二个 stage 有 0.45N 个（720 MB），其余 stage 加起来不到 80 MB。

200M 点的实测结果（`probe.cpp`）：

| | plan.data | temp | 峰值 RSS |
|---|---|---|---|
| 复数 f32，out-of-place | 1.49 GiB | 1.49 GiB | 5.96 GiB |
| 复数 f32，in-place | 1.49 GiB | 1.49 GiB | 4.48 GiB |
| 复数 f64，in-place | 2.98 GiB | 2.98 GiB | 8.95 GiB |
| 复数 f64，out-of-place | 2.98 GiB | 2.98 GiB | 11.9 GiB（按公式推算） |
| 实数 f64（`dft_plan_real`） | 2.24 GiB | 1.49 GiB | 6.71 GiB |

峰值 RSS = 用户缓冲区 + plan.data + temp。plan.data 和 temp 的大小在 aarch64（Clang，neon64，qemu）和 x86 上完全一致。

另外两点需要注意：
- 用 `kfr::dft()` / `idft()` 这类便捷函数时，plan 会被 `dft_cache` 一直缓存，函数返回后 plan.data 也不会释放。
- 如果 N 分解掉 2–10 的因子后，剩下的部分 ≥ 101（即含有较大的质因子），KFR 会改用 Bluestein 算法，内部再建一个 next_pow2(2N−1) 点的 plan，内存会再翻好几倍。

## 不改代码就能省的

1. **in-place 执行**：`out == in`，可以省掉一个缓冲区。
2. **实数输入用 `dft_plan_real`**：内存约减半。
3. **不要用 `dft()` 便捷函数**：自己创建 plan，用完就释放。多个 plan 可以共用同一块 temp。

## 四步法（four-step）：内存降到理论下限，速度更快

`fourstep.hpp` 只用 KFR 的公开接口实现，不需要改 KFR 源码。把 N 分解为 N1 × N2：先对 N2 列分别做 N1 点 DFT 并乘旋转因子 ω_N^(n2·k1)，再对 N1 行分别做 N2 点 DFT。KFR 只需要创建 N1 点和 N2 点两个小 plan，旋转因子由两张约 √N 大小的表现算。

两种调用方式，输出都是自然顺序，逆变换同样不做 1/N 归一化（和 `dft_plan::execute` 一致）：

| 接口 | 输入 | 峰值内存 |
|---|---|---|
| `execute(out, in)` | 保留 | in + out（只比数据本身多几 MB） |
| `execute_inplace(x)` | 原地覆盖 | 只有 x 本身（只多几 MB） |

这两个值已经是对应用法的理论下限，不可能更小了。

### 数据流

- **`execute`（out-of-place）**：不需要转置，也不需要额外缓冲区。
  - 第一步按块读取 `in` 的若干列（跨行读取），做 N1 点 DFT 并乘旋转因子，结果连续写到 `out[n2*N1 + k1]`。
  - 第二步按块读取 `out` 的若干列，做 N2 点 DFT，写回原位置，结果正好是自然顺序的 `X[k1 + N1*k2]`。
- **`execute_inplace`**：两步都在 `[k1][n2]` 布局上完成，每个块都写回读取它的位置。最后把 N1×N2 矩阵原地转置：
  - 先按"行"为单位搬移（环路跟随，只需要一行大小的暂存，几十 KB）；
  - 再对 N1×N1（或 N2×N2）的方阵块做原地转置（8×8 分块）。
  - 这要求 N1 整除 N2，或者 N2 整除 N1，所以建 plan 时要加 `options.inplace = true`，让它只在满足条件的拆分里挑。
  - 如果 N 没有这样的拆分（例如只能拆成 1500 × 1000，互不整除），会退化成使用一块 N 点工作区，此时内存为 2N。可以用 `inplace_without_work()` 查询。
- **N1×N2 的选择**：建 plan 时在当前机器上测量各候选长度子 FFT 的单点耗时，取总耗时最小的组合（约 0.1–0.5 s）。不同长度的子 FFT 单点耗时能差 2 倍以上，排名和 CPU 有关，所以现场测。也可以用 `options.n1` 固定。块大小默认 16，读取、写回按行做软件预取。

### 200M 点实测（x86 单线程，每项 5 次取中位数，同一轮测完）

"SSE4.1" 表示强制 KFR 使用 128 位 SIMD，和 NEON 宽度相同，作为 ARM 的近似。KFR 直接计算的时间不含建 plan（4–9 s），四步法建 plan 不到 0.2 s。

| 类型 | SIMD | 方式 | 时间 | 峰值内存 | 相对 KFR 直接计算 |
|---|---|---|---|---|---|
| f32 | AVX-512 | KFR 直接计算（out-of-place） | 4.43 s | 5.97 GiB | 基准 |
| f32 | AVX-512 | KFR 直接计算（原地） | 4.36 s | 4.47 GiB | |
| f32 | AVX-512 | 四步法 `execute` | 2.62 s | 2.99 GiB | 快 41%，内存 −50% |
| f32 | AVX-512 | 四步法 `execute_inplace` | 2.74 s | **1.51 GiB** | 快 38%，内存 −75%（对比 KFR 原地：−66%） |
| f64 | AVX-512 | KFR 直接计算（out-of-place） | 7.10 s | 11.93 GiB | 基准 |
| f64 | AVX-512 | KFR 直接计算（原地） | 6.83 s | 8.95 GiB | |
| f64 | AVX-512 | 四步法 `execute` | 3.77 s | 5.98 GiB | 快 47%，内存 −50% |
| f64 | AVX-512 | 四步法 `execute_inplace` | 3.91 s | **2.99 GiB** | 快 45%，内存 −75%（对比 KFR 原地：−67%） |
| f32 | SSE4.1 | KFR 直接计算（out-of-place） | 4.42 s | 5.96 GiB | 基准 |
| f32 | SSE4.1 | KFR 直接计算（原地） | 4.06 s | 4.47 GiB | |
| f32 | SSE4.1 | 四步法 `execute` | 3.02 s | 2.99 GiB | 快 32%，内存 −50% |
| f32 | SSE4.1 | 四步法 `execute_inplace` | 3.10 s | **1.51 GiB** | 快 30%，内存 −75% |
| f64 | SSE4.1 | KFR 直接计算（out-of-place） | 7.47 s | 11.93 GiB | 基准 |
| f64 | SSE4.1 | KFR 直接计算（原地） | 7.31 s | 8.95 GiB | |
| f64 | SSE4.1 | 四步法 `execute` | 4.43 s | 5.97 GiB | 快 41%，内存 −50% |
| f64 | SSE4.1 | 四步法 `execute_inplace` | 4.90 s | **3.00 GiB** | 快 34%，内存 −75% |

每种配置下，四步法在时间和内存两个方向上都严格优于 KFR 的同类调用，没有需要取舍的情况。

**与上一版相比**（f32 AVX-512）：保留输入的模式从 3.44 s / 4.49 GiB 变成 2.62 s / 2.99 GiB；原地模式从 4.15 s / 3.01 GiB 变成 2.74 s / 1.51 GiB。

### 各阶段耗时（f32，原地，N1=2500，N2=80000，每次执行）

| 阶段 | 耗时 |
|---|---|
| 第一步：读取转置 | 0.28 s |
| 第一步：N1 点 KFR FFT | 0.63 s |
| 第一步：乘旋转因子并写回 | 0.50 s |
| 第二步：N2 点 KFR FFT | 0.69 s |
| 整行搬移 | 0.17 s |
| 方阵转置 | 0.39 s |

- KFR 自己的子 FFT 约占一半（1.3 s）。
- 其余基本受内存带宽限制：方阵转置改成 8×8 分块后耗时没有变化。
- 所以单线程下再大幅提速的空间不大，下一步应该是多线程。各列、各行之间互相独立，可以直接并行。

### 参数

调过块大小 B（8/16/32/64）、预取距离、N1 的取值，结果在测量噪声（±0.15 s）范围内，默认值已经取在平坦区域。B=64 在原地模式下明显变慢（3.4 s）。

### 2 的幂长度（2²⁷ = 134,217,728）

| 类型 | 方式 | 时间 | 峰值内存 |
|---|---|---|---|
| f32 | KFR 直接计算（out-of-place） | 1.69 s | 3.00 GiB |
| f32 | KFR 直接计算（原地） | 1.56 s | 2.00 GiB |
| f32 | 四步法 `execute` | 2.10 s | 2.01 GiB |
| f32 | 四步法 `execute_inplace` | 1.53 s | **1.02 GiB** |
| f64 | KFR 直接计算（原地） | 2.64 s | 4.00 GiB |
| f64 | 四步法 `execute_inplace` | 2.67 s | **2.01 GiB** |

2 的幂长度下 KFR 本身有专门的优化，所以：
- **原地**：速度相同，内存减半，仍然值得换成四步法。
- **out-of-place**：四步法比 KFR 慢约 24%，内存少 1 GiB，属于时间换内存，按需选择。

### 精度

f32/f64 结果对比 f64 直接计算的相对 RMS 误差，四步法和 KFR 直接计算在同一量级：

| N | 类型 | KFR 直接计算 | 四步法 | 正反变换往返 |
|---|---|---|---|---|
| 1M | f32 | 2.41e-7 | 2.43e-7 | 2.79e-7 |
| 2M | f32 | 2.33e-7 | 2.30e-7 | 2.63e-7 |
| 10M | f32 | | 2.49e-7 | 3.14e-7 |
| 2M | f64 | 参考 | 4.6e-16 | 4.7e-16 |

### 验证

- x86：1M–10M 点，f32/f64；N1 大于 N2、N1 小于 N2、N1 等于 N2、N1 不是 8 的倍数（方阵转置的边缘部分）；用工作区的退化路径；`execute` 之后输入保持不变。
- aarch64（Clang + neon64，qemu）：2M（f32/f64）、3.6M、16M，以及强制 N1 取 500、2000 的情况，上述所有检查全部通过。
- qemu 下的耗时没有参考价值，ARM 上的速度需要真机确认。

### 什么时候不能用

- **N 含大于 100 的质因子**：找不到合适的拆分，`find_split(n)` 返回 0，这时退回 `dft_plan`。
- 实数输入（`dft_plan_real`）：这里只实现了复数 DFT，没有对应的实数版本。

### 限制和后续

- 还没有做多线程。
- 列读取、旋转因子乘法和转置依赖编译器自动向量化，没有手写 NEON。
- 性能必须在 ARM 真机上用 `run_bench.sh` 确认。

## KFR 最新版（7.x）

- 新增了一个基于四步法思路的 FFT 实现（`src/dft/sandwich.hpp`，`ngfft`），但只支持 **2 的幂**，而且需要 **C++20**。它中间那一步的旋转因子仍然按 N 个存储（`sandwich_twiddle_size` 里的 `r1 * r2`）。
- **非 2 的幂的路径**（`init_dft`）和 6.3.1 基本相同，只是因子分解改成了质因数分解。每个 stage 仍有自己的旋转因子表，总量约 N，scratch 也仍是 N。
- 结论：升级到 7.x 解决不了 200M 点的内存问题，而且你们的 C++17 环境也用不了 7.x。

## 文件

| 文件 | 说明 |
|---|---|
| `probe.cpp` | 打印 plan.data、temp_size 和各 stage（`DUMP=1`），测峰值 RSS |
| `fourstep.hpp` | 四步法实现：`execute`（保留输入）、`execute_inplace`（原地） |
| `bench.cpp` | 精度检查（`check`），以及 KFR 直接计算和四步法各模式的内存、耗时对比 |
| `run_bench.sh` | 在目标机器上编译 `bench.cpp` 并跑完整对比 |

```bash
# aarch64，KFR 由 ../kfr-6.3.1-clang/build-clang.sh 安装到 $KFR
./run_bench.sh --kfr $KFR --cxx clang++ --n 200000000
```
