# KFR 6.3.1：大点数 DFT 的内存占用分析

问题：200M 点的 DFT 占用约 10 GB 内存。

## 内存都用在哪里

`dft_plan<T>(N)` 除了用户自己的输入、输出缓冲区以外，还需要两块大小约为 N 个复数的内存：

| 内存块 | 大小 | 来源 |
|---|---|---|
| `plan.data`（旋转因子表） | ≈ N × sizeof(complex&lt;T&gt;) | 每个 stage 存 `repeats × (radix−1)` 个旋转因子，各 stage 加起来正好约等于 N−1 |
| `plan.temp_size`（scratch） | ≈ N × sizeof(complex&lt;T&gt;) | 各 stage 都是 out-of-place 计算，最后还有一个 reorder stage，所以中间结果需要一块乒乓缓冲区 |

以 200,000,000 = 2⁹·5⁸ 为例，KFR 把它分解为 1 个 radix-2 stage 和 8 个 radix-10 stage，再加 1 个 reorder stage。其中第一个 stage 的旋转因子表就有 N/2 个复数（f32 下 800 MB），第二个 stage 有 0.45N 个（720 MB），其余 stage 加起来不到 80 MB。

200M 点的实测结果（`probe.cpp`）：

| | plan.data | temp | 峰值 RSS |
|---|---|---|---|
| 复数 f32，out-of-place | 1.49 GiB | 1.49 GiB | 5.96 GiB |
| 复数 f32，in-place | 1.49 GiB | 1.49 GiB | 4.48 GiB |
| 复数 f64，in-place | 2.98 GiB | 2.98 GiB | 8.95 GiB |
| 复数 f64，out-of-place | 2.98 GiB | 2.98 GiB | 11.9 GiB（按公式推算） |
| 实数 f64（`dft_plan_real`） | 2.24 GiB | 1.49 GiB | 6.71 GiB |

峰值 RSS = 用户缓冲区 + plan.data + temp。plan.data 和 temp 的大小在 aarch64（Clang，neon64，qemu）和 x86 上完全一致。

另外两点需要注意：
- 用 `kfr::dft()` / `idft()` 这类便捷函数时，plan 会被 `dft_cache` 一直缓存，函数返回后 plan.data 也不会释放。
- 如果 N 分解掉 2–10 的因子后，剩下的部分 ≥ 101（即含有较大的质因子），KFR 会改用 Bluestein 算法，内部再建一个 next_pow2(2N−1) 点的 plan，内存会再翻好几倍。

## 不改代码就能省的

1. **in-place 执行**：`out == in`，可以省掉一个缓冲区。
2. **实数输入用 `dft_plan_real`**：内存约减半。
3. **不要用 `dft()` 便捷函数**：自己创建 plan，用完就释放。多个 plan 可以共用同一块 temp。

## 四步法（four-step）：内存降到理论下限，速度更快

`fourstep.hpp`（复数）和 `fourstep_real.hpp`（实数）只用 KFR 的公开接口实现，不需要改 KFR 源码。把 N 分解为 N1 × N2：先对 N2 列分别做 N1 点 DFT 并乘旋转因子 ω_N^(n2·k1)，再对 N1 行分别做 N2 点 DFT。KFR 只需要创建 N1 点和 N2 点两个小 plan，旋转因子由两张约 √N 大小的表现算。

### 接口（Pareto 上的各个点）

输出都是自然顺序，逆变换不做归一化（和 `dft_plan` 一致）。

| 接口 | 输入 | 峰值内存 |
|---|---|---|
| `fft_fourstep<T>::execute(out, in)` | 保留 | in + out（比数据本身只多几 MB） |
| `fft_fourstep<T>::execute_inplace(x)` | 原地覆盖 | 只有 x 本身（只多几 MB） |
| `fft_fourstep_real<T>::execute(out, in)`、`inverse(out, in)` | 保留 | N 个实数 + N/2+1 个复数 |
| `fft_fourstep_real<T>::execute_inplace(x)`、`inverse_inplace(x)` | 原地覆盖 | N+2 个实数（只有数据本身） |

- **实数版**的输出格式和 `dft_plan_real`（`dft_pack_format::CCs`）相同，N/2+1 个复数频点。做法是把 N 个实数当作 N/2 个复数做一次复数四步法，再对 (k, M−k) 成对的频点做一遍后处理。这一遍也是原地完成的。
- **多线程是可选的**：每个接口都有一个带 `std::vector<workspace>` 和 `parallel_for_t` 的重载。库默认不开线程。`parallel_for_t` 是一个回调：对 [0, count) 里的每个块调用 `body(item, worker)`，可以接 `thread_executor(n)`（内置，基于 `std::thread`）、线程池、OpenMP 或任务系统。
  - 每个线程只多占一个工作区，几 MB。
  - 并行结果和串行逐位一致。
- **plan 与工作区分离**：plan 本身不可变（子 plan 和旋转因子表），每次调用的临时空间放在 `workspace` 里。同一个 plan 可以被多个线程同时使用，每个线程一个工作区。不带工作区的重载使用内部工作区，不是线程安全的。

### 数据流

- **`execute`（out-of-place）**：没有转置，也没有额外缓冲区。第一步读取 `in` 的若干列、做 DFT 并乘旋转因子，结果连续写到 `out[n2*N1 + k1]`；第二步读取 `out` 的若干列、做 DFT，写回原位置，结果正好是自然顺序的 `X[k1 + N1*k2]`。
  - 当 N1 是 2 的幂时（例如 N 本身是 2 的幂），第二步的跨行访问会在缓存里互相冲突，改用"拷贝 + 原地"更快（2²⁷：1.84 s 对 2.18 s，内存相同）。`execute` 会自动选。
- **`execute_inplace`**：两步都在 `[k1][n2]` 布局上完成，每个块写回读取它的位置，最后把 N1×N2 矩阵原地转置：先按整行搬移（环路跟随，只要一行大小的暂存），再对方阵块做 8×8 分块的原地转置。
  - 这要求 N1 整除 N2，或者 N2 整除 N1。默认选项会在这样的拆分里挑，除非它比最优拆分慢超过 `inplace_slack`（5%）。`options::for_inplace()` 强制选这样的拆分。
  - 没有这样的拆分时，该次调用会临时分配一块 N 点缓冲区并在调用结束时释放。`inplace_without_work()` 可以查询。
- **N1×N2 的选择**：建 plan 时在当前机器上测量各候选长度子 FFT 的单点耗时，先粗测排名，再对前几名加大测量力度，最后取总耗时最小的（约 0.2–0.5 s）。子 FFT 长度的上限跟着 L2 缓存走（`l2_cache_bytes()`，取 L2 的一半，限制在 128 KiB–1 MiB）。

### 200M 点实测（x86 单线程，同一轮测完）

测试机是 4 核 Xeon，L2 每核 2 MiB，L3 260 MiB。"中位数"是同一配置跑 3 次的中位数。**这台机器同一配置前后两轮的耗时能差 20%**，所以下面凡是写了"A/B 比值"的，都是在同一个进程里交替运行两种方式、取逐对比值的中位数（括号里是最小到最大），这样才能比较。KFR 直接计算的时间不含建 plan（4–10 s），四步法建 plan 不到 0.6 s。

**复数 200M 点（AVX-512）**

| 类型 | 方式 | 时间（中位数） | 峰值内存 |
|---|---|---|---|
| f32 | KFR 直接计算（out-of-place） | 4.38 s | 5.97 GiB |
| f32 | KFR 直接计算（原地） | 4.26 s | 4.48 GiB |
| f32 | 四步法 `execute` | 2.79 s | 3.00 GiB |
| f32 | 四步法 `execute_inplace` | 2.81 s | **1.51 GiB** |
| f64 | KFR 直接计算（out-of-place） | 7.16 s | 11.93 GiB |
| f64 | KFR 直接计算（原地） | 6.80 s | 8.95 GiB |
| f64 | 四步法 `execute` | 3.78 s | 5.97 GiB |
| f64 | 四步法 `execute_inplace` | 4.17 s | **2.99 GiB** |

- A/B 比值：f32 保留输入（四步法对 KFR out-of-place）0.64（0.59–0.67）；f32 原地（四步法对 KFR 原地）0.78（0.73–0.82）。
- 后一个比值里，四步法原地选到了偏慢的拆分（10000×20000，3.2 s）。选 2500×80000 时是 2.7 s，比值约 0.66。见下面的"选择拆分"。
- f64 的 A/B 没有测：两个 f64 的 200M 点计划加三个缓冲区超过了这台机器 15 GB 的内存，所以只给单次运行的中位数。
- 在 SSE4.1（128 位 SIMD，和 NEON 宽度相同）下，上一轮的单次运行结果是同样的趋势：f32 保留输入快 32%、原地快 30%，f64 快 41% 和 34%。

**实数 200M 个样本（AVX-512，KFR 对比对象是 `dft_plan_real`）**

| 类型 | 方式 | 时间（中位数） | 峰值内存 |
|---|---|---|---|
| f32 | KFR `dft_plan_real` | 2.24 s | 3.36 GiB |
| f32 | 四步法 `execute`（保留输入） | 1.47 s | 1.51 GiB |
| f32 | 四步法 `execute_inplace` | 1.30 s | **0.76 GiB** |
| f64 | KFR `dft_plan_real` | 3.26 s | 6.71 GiB |
| f64 | 四步法 `execute`（保留输入） | 2.44 s | 2.99 GiB |
| f64 | 四步法 `execute_inplace` | 2.35 s | **1.50 GiB** |

A/B 比值（四步法原地对 KFR）：f32 0.59（0.57–0.63），f64 0.64（0.61–0.66）。内存降到 KFR 的 1/4–1/5。

**多线程（opt-in，f32 复数 200M 原地，A/B 对单线程）**

| 线程数 | 耗时比 | 加速 |
|---|---|---|
| 2 | 0.54（0.51–0.56） | 1.9× |
| 4 | 0.30（0.30–0.31） | 3.3× |

- f64 复数原地用 4 线程是 0.31，f32 实数原地用 4 线程是 0.33。
- 每个线程只多占一个几 MB 的工作区。
- 串行的部分只有整行搬移（0.16 s）。
- 这台机器 4 核。ARM 服务器单核带宽通常只占整颗芯片的一小部分，所以多线程在真机上的收益预计更大，但需要真机确认。

**2 的幂长度（2²⁷ = 134,217,728，f32，A/B）**

| 比较 | 比值 | 峰值内存 |
|---|---|---|
| 四步法 `execute_inplace` 对 KFR 原地 | 1.02（1.00–1.07） | 1.02 GiB 对 2.00 GiB |
| 四步法 `execute` 对 KFR out-of-place | 1.01（0.98–1.03） | 2.01 GiB 对 3.00 GiB |

2 的幂长度下 KFR 自身有专门的优化，四步法在速度上持平，内存少 1/3 到 1/2。

### 选择拆分

分解 N = N1 × N2 的选择对速度有影响，但无法只靠子 FFT 的计时预测：
- 200M f32 原地，强制不同拆分的耗时在 2.65–3.20 s 之间，大多数在 2.8–2.95 s，个别（10000×20000、80000×2500）慢 10% 以上，没有单调规律。
- 在各阶段的计时里，差别主要出现在"乘旋转因子并写回"这一步：N1 越大，每个块要写的分散行越多，耗时从 0.55 s（N1=2000）涨到 0.92 s（N1=10000）。

所以提供了一个可选的 `autotune(n, options, inplace)`：在目标机器上用真实尺寸把最有希望的几个拆分各跑几次，返回最快的拆分。用一次，把得到的 `options.n1` 固定下来即可。需要的内存和执行时一样（原地 N，out-of-place 2N）。`run_bench.sh` 会自动运行并输出每个候选的耗时。
- 200M f32 原地：试了 6 个，耗时 2.84–3.20 s，选了 40000×5000（2.84 s）。
- 200M f32 out-of-place：试了 6 个，耗时 2.57–2.86 s，选了 5000×40000（2.57 s）。
- 200M f64 原地：4 个候选都在 4.08–4.30 s，差别不大。

### 原地与 out-of-place 的取舍

原地模式比 out-of-place 多一遍转置访存，f32 约慢 0–7%，f64 约慢 10%，换来内存减半。两者都明显快于 KFR 同类调用。

### 调优参数

块大小 B（8/16/32/64）、预取距离、N1，在测量噪声（±0.15 s）内影响不大，默认值取在平坦区域。B=64 在原地模式下明显变慢（3.4 s）。

### 精度

f32/f64 结果对比 f64 直接计算的相对 RMS 误差，四步法和 KFR 同一量级：

| N | 类型 | KFR | 四步法 | 往返 |
|---|---|---|---|---|
| 2M | f32 复数 | 2.33e-7 | 2.30e-7 | 2.63e-7 |
| 2M | f32 实数 | 1.92e-7 | 1.89e-7 | 2.97e-7 |
| 781,250 | f32 实数（M 为奇数） | 2.50e-7 | 2.44e-7 | 3.33e-7 |
| 2M | f64 复数 | 参考 | 4.6e-16 | 4.7e-16 |
| 4M | f64 实数 | 参考 | 3.5e-16 | 4.9e-16 |

### 验证

- **x86**：f32/f64，78 万–1677 万点；N1 大于、小于、等于 N2；N1 不是 8 的倍数（方阵转置的边缘部分）；M 为奇数的实数；用临时缓冲区的退化路径；`execute` 后输入保持不变；双线程共用一个 plan；多线程结果与串行逐位一致（复数和实数，正反变换）。
- **aarch64**（Clang + neon64，qemu）：2M（f32/f64）、3.6M、4.2M、781,250（f32/f64），复数、实数、多线程，全部通过。
- qemu 下的耗时没有参考价值，ARM 上的速度需要真机确认。

### 什么时候不能用

- N（实数时为 N/2）含大于 100 的质因子：找不到合适的拆分，`find_split(n)` 返回 0，这时退回 `dft_plan`。

### 限制和后续

- 列读取、旋转因子乘法和转置依赖编译器自动向量化，没有手写 NEON。这些步骤是内存带宽受限的（方阵转置改成 8×8 分块后耗时完全没变），手写向量化的收益预计有限。
- **ARM 真机上的数据还没有**：缓存大小、页大小和单核带宽都和这台测试机差别很大。用 `run_bench.sh` 在真机上跑一次，会输出系统信息、精度、内存对比、A/B 比值、`autotune` 结果、块大小扫描和线程扩展。

## KFR 最新版（7.x）

- 新增了一个基于四步法思路的 FFT 实现（`src/dft/sandwich.hpp`，`ngfft`），但只支持 **2 的幂**，而且需要 **C++20**。它中间那一步的旋转因子仍然按 N 个存储（`sandwich_twiddle_size` 里的 `r1 * r2`）。
- **非 2 的幂的路径**（`init_dft`）和 6.3.1 基本相同，只是因子分解改成了质因数分解。每个 stage 仍有自己的旋转因子表，总量约 N，scratch 也仍是 N。
- 结论：升级到 7.x 解决不了 200M 点的内存问题，而且你们的 C++17 环境也用不了 7.x。

## 文件

| 文件 | 说明 |
|---|---|
| `probe.cpp` | 打印 plan.data、temp_size 和各 stage（`DUMP=1`），测峰值 RSS |
| `fourstep.hpp` | 复数四步法：`execute`（保留输入）、`execute_inplace`（原地）、可选多线程、`autotune` |
| `fourstep_real.hpp` | 实数四步法（基于 `fourstep.hpp`）：正反变换，保留输入和原地两种 |
| `bench.cpp` | 精度和线程检查（`check`）、各模式的内存和耗时、同进程 A/B 交替对比（`ab`）、`tune`；用法见文件开头 |
| `run_bench.sh` | 在目标机器上编译 `bench.cpp` 并跑完整对比，输出保存到 `report.txt` |

```bash
# aarch64，KFR 由 ../kfr-6.3.1-clang/build-clang.sh 安装到 $KFR
./run_bench.sh --kfr $KFR --cxx clang++ --n 200000000
```
